# Agentic CEO Dashboard — Subsystem A: Chat + Query Layer

**Status:** Design approved 2026-06-07 by Jim
**Author:** Claude (via brainstorming skill, in collaboration with Jim)
**Repo:** `voom-ceo-dashboard`
**Depends on:** none (this is the foundation)
**Blocks:** Subsystems B (action layer), C (proactive insight), D (self-improvement loop)

---

## 1. Context

The VOOM CEO dashboard is currently a 16-page read-mostly admin console with 59 API routes, zero LLM integration, and zero background jobs. Every interaction is Jim clicking. The goal of this work is to add a natural-language query surface so Jim can ask "how many signups today by city" and get an answer in seconds, on phone or desktop.

This spec covers **only subsystem A** of a four-subsystem roadmap:
- **A — Chat + query layer** (this spec)
- B — Action layer (separate spec, depends on A)
- C — Proactive insight layer (separate spec, depends on A)
- D — Self-improvement loop (separate spec, depends on A/B/C)

## 2. Goal

Jim can ask anything the existing dashboard could answer with clicks, plus anything the schema can express, by typing or speaking a natural-language question from any page on the dashboard, on mobile or desktop, and getting an accurate answer with an inline chart in under 5 seconds, with zero risk of state mutation.

## 3. Non-goals (for A specifically)

- No writes. No mutations. No actions. (That is subsystem B.)
- No scheduled or proactive runs. The agent only runs when Jim taps. (That is subsystem C.)
- No multi-agent orchestration. One agent, one model. (Hermes architecture is North Star, deferred.)
- No cross-thread memory. Each thread is self-contained.
- No voice synthesis output. Text-to-speech is out of scope; speech-to-text input is in (browser native).

## 4. User experience

### 4.1 Surface

A floating circular button bottom-right on every dashboard page (mobile and desktop), hidden on `/vendor/register` (the gamified signup flow) and on any full-screen modal page.

Tapping it opens a chat surface:
- **Mobile**: a bottom sheet that slides up to 90% viewport. Drag-down to dismiss.
- **Desktop**: a right-side panel, 480px wide, push-not-overlay.

The surface contains:
- A thread list (collapsed by default on mobile, sidebar on desktop)
- The active conversation
- An input box with a microphone affordance (uses browser `SpeechRecognition` API, no external service)
- Below the input: 3 suggested follow-up chips, generated by the agent at the end of each response

### 4.2 Context-awareness

When the chat is opened, the client sends the agent a structured context block:

```json
{
  "current_page": "/vendors",
  "active_filters": { "city": "Accra", "tier": "free" },
  "selected_entity": null,
  "time": "2026-06-07T14:32:00Z",
  "viewport": "mobile"
}
```

The agent uses this to disambiguate pronouns. "Show me their listings" on the Vendors page filtered to Accra means *those vendors*, not all vendors.

### 4.3 Thread persistence

Threads persist indefinitely in the `agent_threads` and `agent_messages` tables. Jim can revisit any past thread. Threads are auto-titled by the agent after the first exchange.

### 4.4 Voice rules (baked into system prompt)

- Never em dashes or en dashes. Hyphens fine. (Per Jim's `feedback_no_em_dashes_in_outbound_copy` memory.)
- 4th-grade reading level when drafting anything user-facing (vendor messages, copy). (Per `feedback_voom_copy_reading_level`.)
- "48K" is monthly site visits, never users/MAUs. (Per `feedback_voom_traffic_not_users`.)
- Never expose internal markers (`[ref:market_anchor]` etc) in user-facing drafts. (Per `feedback_no_internal_markers_in_user_copy`.)
- Never assert on-the-ground presence in Ghana. (Per `user_jim_role`.)

### 4.5 Honesty rules (baked into system prompt)

- If a tool errored, say so explicitly.
- If the schema cannot answer the question, say so and propose what can be answered with available data.
- Never invent vendor names, phone numbers, GHS amounts, or counts.
- Every concrete claim must trace to a tool result. UI shows tool calls collapsibly so Jim can audit.

## 6. Tool registry

Every tool has a typed input schema (Zod), a typed output, and a 1-line description the LLM sees.

| Tool | Wraps | Notes |
|---|---|---|
| `list_vendors(filters)` | `GET /api/vendors` | filters: city, tier, status, hasListings, businessName |
| `get_vendor(id)` | `GET /api/vendors/:id` | returns full profile + last 5 orders + listing count |
| `get_metrics(range, slice)` | `/api/stats`, `/growth`, `/revenue` | range: today/7d/30d/90d/custom; slice: optional dim |
| `get_funnel(period)` | `/api/analytics/funnel` | signup, listing, buyer-search funnels |
| `get_supply_demand_gaps()` | `/api/analytics/supply-demand` | parts buyers search that no one lists |
| `get_part_requests(filters)` | `/api/part-requests` | filters: status, vehicleMake, minBudget |
| `get_whatsapp_leads(filters)` | `/api/whatsapp/leads` | filters: status, real vs test, since |
| `get_orders(filters)` | `/api/orders` | filters: status, vendorId, since, minTotal |
| `get_verification_queue()` | `/api/verification-queue` | pending Ghana Card review |
| `run_sql(query)` | curated read-only views | the catch-all |
| `render_chart(spec)` | UI-side | spec: type (line/bar/pie/area), data, x, y, title |

The model gets the full tool list in the system prompt (cached). Per turn, the agent can call up to 8 tools (hard cap to prevent loops). Tool calls run in parallel where the agent emits them in one batch.

## 7. `run_sql` safety — three stacked layers

This is the only tool that could surface data the curated wrappers don't already expose, so it gets defense in depth.

### Layer 1 — DB role

A new Postgres role `voom_dashboard_agent` with `SELECT` only, granted only on a curated set of views under schema `agent_views`. The role has no access to base tables, no functions other than allowlisted aggregates, no DDL.

### Layer 2 — Parser

Every query is parsed with `pgsql-ast-parser`. Rejected if:
- Multiple statements
- Anything other than a top-level `SELECT`
- A `WITH` clause containing a writing CTE (`INSERT`/`UPDATE`/`DELETE`)
- A function call outside the allowlist (no `pg_read_file`, no `dblink`, no `copy`, etc)
- Any reference to a table outside `agent_views`

### Layer 3 — System prompt rules

The schema dump given to the agent explicitly tells it:
- Every camelCase column must be double-quoted (per `reference_postgres_camelcase_quoting`)
- Enum columns must use `::text` for `LIKE`/`SIMILAR TO` (per `reference_postgres_enum_text_cast`)
- Use `agent_views.*`, never base tables
- Prefer the typed wrapper tools when they cover the question

### Curated views (initial set)

| View | Source | PII excluded |
|---|---|---|
| `agent_views.vendors_summary` | `vendors` joined to listing counts | phone, ghanaCardNumber, idDocumentUrl |
| `agent_views.products_summary` | `products` joined to vendor city | seller phone |
| `agent_views.orders_summary` | `orders` joined to vendor + buyer city | buyer phone, buyer email |
| `agent_views.analytics_events_summary` | `analytics_events` last 90d | userId hashed, ipAddress excluded |
| `agent_views.part_requests_summary` | `part_requests` last 60d | requester phone |
| `agent_views.users_summary` | `users` minus PII | phone, email, passwordHash |

Views are version-controlled in `migrations/`. Adding a new view requires a migration and a code review.

## 8. Data model

```sql
CREATE TABLE agent_threads (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title         TEXT,  -- agent-generated after first exchange
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_message_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE agent_messages (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  thread_id     UUID NOT NULL REFERENCES agent_threads(id) ON DELETE CASCADE,
  role          TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'tool')),
  content       TEXT NOT NULL,
  tool_calls    JSONB,  -- array of {tool, args, result_id}
  tool_results  JSONB,  -- array of {tool_use_id, content, is_error}
  tokens_in     INTEGER,
  tokens_out    INTEGER,
  cost_cents    NUMERIC(10, 4),  -- fractional cents allowed
  latency_ms    INTEGER,
  feedback      SMALLINT,  -- -1, 0 (default), +1
  page_context  JSONB,     -- captured client-side at message-send
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_agent_messages_thread ON agent_messages(thread_id, created_at);
CREATE INDEX idx_agent_messages_feedback ON agent_messages(feedback) WHERE feedback != 0;

-- Daily spend tracking
CREATE TABLE agent_daily_spend (
  day           DATE PRIMARY KEY,
  cents_spent   NUMERIC(10, 4) NOT NULL DEFAULT 0,
  message_count INTEGER NOT NULL DEFAULT 0,
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

No changes to the marketplace's existing tables.

## 9. System prompt

Composed from three parts, all cached:

1. **VOOM context** (~1K tokens): who Jim is, what VOOM does, what the dashboard does, who the marketplace serves, the business model, current state (fundraise, runway, Justice in Accra).
2. **Schema dump** (~5K tokens): every `agent_views.*` view with column names, types, 1-line meaning, and the camelCase + enum cast reminders.
3. **Tool catalog** (~1K tokens): every tool with input schema and 1-line usage example.
4. **Voice and honesty rules** (~500 tokens): the rules from sections 4.4 and 4.5.

Total cached input: ~7.5K tokens. Anthropic charges 10% of input cost for cache reads, so this is cheap at Jim's volume.

The schema dump is regenerated nightly by `server/agent/schema-introspect.ts` from live Supabase introspection, written to `data/agent-schema.json`, and loaded at process start. Manual `pnpm agent:refresh-schema` available.

## 9.5. Rate and spend limits

Three hard caps stack:

| Cap | Default | Env var | Behavior on hit |
|---|---|---|---|
| Messages per hour | 30 | `MAX_AGENT_MESSAGES_PER_HOUR` | 429 returned, friendly UI message, retry-after header |
| Messages per day | 200 | `MAX_AGENT_MESSAGES_PER_DAY` | 429 returned, friendly UI message |
| Spend per day (cents) | 500 ($5) | `MAX_DAILY_AGENT_SPEND_CENTS` | 429 returned, notification to `sales@voomparts.com` |
| Tool calls per turn | 8 | `MAX_TOOL_CALLS_PER_TURN` | Agent forced to wrap up |
| Output tokens per response | 4096 | (Anthropic SDK param) | Response truncated cleanly |

Single-user assumption holds — these caps are safety belts against runaway loops, not abuse defense.

## 10. Cost model

Claude Sonnet 4.6 pricing (as of 2026-01):
- Input: $3 / M tokens (cached: $0.30 / M)
- Output: $15 / M tokens

Typical turn for Jim:
- Cached input: 7.5K tokens → $0.0023
- Fresh input (thread history + new message + page context + tool results): ~2K tokens → $0.006
- Output: ~500 tokens → $0.0075
- **Per-turn: ~$0.016, i.e. 1.6 cents**

At 50 turns/day: ~$0.80/day. At the 200/day hard cap: ~$3.20/day.

`MAX_DAILY_AGENT_SPEND_CENTS` env var defaults to **500 cents ($5)**. When hit, the agent returns a friendly "I've hit today's spending limit, ping Jim if this is urgent" message and a notification routes to `sales@voomparts.com` (per `reference_voom_notification_emails`).

## 12. Risk table

| Risk | Likelihood | Severity | Mitigation |
|---|---|---|---|
| Agent hallucinates a vendor name, phone, or GHS number | Medium | High | System prompt forbids invention; every concrete claim must trace to a tool result; UI exposes the tool calls; +1/-1 feedback surfaces hallucinations for the D loop later |
| `run_sql` reads PII it shouldn't display | Low | High | Three-layer containment: DB role + parser + curated views exclude PII. Worst case is a query that returns nothing useful |
| Cost runaway from a tool-use loop | Low | Medium | Max 8 tool calls per turn; max 4K output tokens; daily spend cap; per-thread message cap |
| Mobile chat sheet covers signup flow | Low | High | Button hides on `/vendor/register` and any route in a maintained block-list |
| Slow on Ghana 3G | Medium | Medium | SSE streaming so first token shows in <500ms; chat JS bundle is lazy-loaded (only when button tapped); schema lives server-side, never shipped to client |
| Schema drifts and answers go stale | Medium | Medium | Nightly schema introspection; `pnpm agent:refresh-schema` available; system prompt cache invalidates when schema file changes |
| `DASHBOARD_API_KEY` leaks → bill blows up | Low | High | Daily spend cap is the backstop. Add `AGENT_ACCESS_TOKEN` rotation if Jim wants belt-and-braces |
| Agent refuses to answer questions it actually could | Medium | Low | Caught by +1/-1 feedback; D loop later proposes prompt or tool improvements |
| `pgsql-ast-parser` misses a class of mutation | Low | High | DB role can't write regardless. Document the parser's known limits in spec |
| Agent gives copy that violates voice rules (em dashes, jargon) | Medium | Low | Rules in system prompt; +1/-1 feedback catches drift; consider a deterministic post-processor for em/en dashes |

## 13. Telemetry to feed D (the self-improvement loop) later

Every agent response logs:
- Tool calls made, latencies, errors
- Tokens in/out and cost
- Page context Jim was on
- Did Jim follow up? With what?
- Did Jim +1 or -1?
- Did Jim then perform a click action (proxy for "satisfied")?

`agent_messages` plus a future `agent_session_outcomes` rollup gives D enough signal to propose new tools, fix broken ones, deprecate unused dashboard pages.

## 16. Acceptance criteria for A1

A1 is done when, on Jim's phone, opening the dashboard, tapping the floating chat button on any page, and asking each of the following yields a correct, sourced, cited answer in <5 seconds:

1. "How many vendors signed up in the last 7 days, by city?"
2. "Show me Accra vendors who are tier=free and have zero listings."
3. "What's GMV this month vs last month?"
4. "Which part requests are open and over GHS 500?"
5. "Show me real WhatsApp leads from the last 48 hours, not test."
6. From the Vendors page filtered to Accra: "tell me about the dormant ones."

All six answers must:
- Be backed by a tool call Jim can audit via "show work"
- Use no em or en dashes
- Not invent any name, phone, or amount
- Cost less than 5 cents combined
